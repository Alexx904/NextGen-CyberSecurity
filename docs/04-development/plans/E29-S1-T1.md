## Identity and compatibility

`backend/internal/domain/assessment_issue.go` owns the new additive types.
Identity consists of tenant UUID, stable asset UUID, transport/port and an
explicit vulnerability/control key. The caller must resolve an asset through
trusted inventory identity; IP address, banner and hostname are not stable IDs.
Unresolved/ambiguous assets cannot create issues. Asset moves preserve identity;
different tenants/assets/endpoints/keys cannot merge. Keys are trimmed but remain
case-sensitive; only protocol is canonicalized. Deduplication uses the complete
comparable identity, never an IP-only fingerprint. No existing DTO changes.

Observations reference immutable finding and scan UUIDs, the same issue identity,
observation time and versioned source provenance. Replaying an identical finding
is idempotent; conflicting reuse of its UUID is rejected. Older observations are
rejected for online ingestion (historical backfill needs a separate design).

## Lifecycle and time policy

States: open, mitigation_applied, correction_declared, corrected_verified.
Operator transitions require an actor and reason. Only a separate verification
record with source/version/reference, complete coverage of this issue and an
explicit not-present result may close a declared correction. Scan absence alone
has no transition. Detection confidence never grants execution permission or
establishes a verified correction. Positive observations reopen any remediated
state; recurrence after closure starts a new MTTR cycle while preserving the
first observation and previous transitions. Duplicate replay cannot reopen.

MTTR is elapsed wall time from first positive observation in the current cycle
to verified correction; no pauses/exclusions. Reopened issues have no completed
current MTTR. SLA is optional, explicit policy ID/version plus positive duration;
no regulatory defaults. Deadline is anchored to cycle start, breach is strictly
after deadline while unresolved. Assignment is optional actor UUID. Policy and
assignment are constructor inputs in this increment; updates need an audited
application command in the persistence increment.

## Next contracts and gates

Persistence must enforce tenant/asset scope, unique identity and observation
references, append-only evidence/transitions, optimistic concurrency and atomic
issue/observation writes. Define repository interfaces, API DTO/errors/auth and
paired schema up/down before adding that layer; do not expose this in-memory
aggregate directly as an HTTP request body. Reports will need a consistent
cutoff and immutable snapshot; domain state alone does not satisfy that gate.

This increment: targeted identity, provenance, replay/conflict, tenant mismatch,
chronology, verification, recurrence and SLA tests; Final Backend (test/vet/build),
Docs, self-review and Doc Sync. No DB/UI change, so PostgreSQL/browser/PDF gates
belong to subsequent persistence/UI/export increments rather than this one.
